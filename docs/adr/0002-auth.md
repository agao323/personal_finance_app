# ADR 0002 — Authentication: Cloudflare Access in front, passkeys inside

Status: accepted · 2026-08-18 · Ticket 036

## Context

One household, two people, real financial data, on the public internet. The app needs
to be reachable from a phone on mobile data and from a laptop anywhere, and it must not
be reachable by anyone else.

The obvious options were a password login, an OAuth provider, or an identity proxy.

## Decision

**Two independent layers.**

1. **Cloudflare Access** on `allofmymoney.com`, with a policy allowing exactly the
   household's identities. Requests from anyone else are refused at the edge and never
   reach the origin.
2. **Passkeys (WebAuthn)** in the application, with the `users` table as the allowlist.

Layer 1 is the security. Layer 2 is real — it runs in production and gates every route
— but if it had a flaw, layer 1 would still be standing.

**No passwords, ever, and no recovery codes.** There is no version of hand-rolled
password auth worth the time and it is the most common way projects like this get
owned. A lost passkey is recovered by re-registering from behind Access, which is a
stronger gate than any recovery flow would be.

## Consequences

**The API has no public address.** A Fly app is publicly addressable by default, and
Access in front of a reachable origin is a false sense of security. The browser talks
only to the Next.js origin, which proxies to the API over Fly's private IPv6 network.
There is exactly one Access application and no second hostname to forget about.

**The origin validates the Access JWT anyway.** `web/src/lib/access.ts` verifies
`Cf-Access-Jwt-Assertion` against Cloudflare's published keys — signature, issuer, and
audience — and returns 403 when it does not verify. In normal operation nothing that
fails this ever arrives; it exists for the case where the Fly app is given a public
address by accident, which is a one-line mistake and otherwise a silent one.

It is **disabled when unconfigured**, so local development and the demo run without a
team domain. `CF_ACCESS_TEAM_DOMAIN` and `CF_ACCESS_AUD` must *both* be set: an
audience with no issuer accepts a token from any Access tenant, and an issuer with no
audience accepts one minted for a different application.

**`sameSite=lax`, not `strict`.** The Access redirect returns the user cross-site, and
`strict` drops the session cookie on exactly that navigation.

**The RP ID is the registrable parent domain**, not a subdomain. A passkey scoped to
`app.allofmymoney.com` stops working the moment anything moves to the apex — which this
project already did once, before any passkey existed. Getting this wrong produces
credentials that work locally and fail in production.

**Sessions are stateless signed cookies.** No server-side revocation; the mitigations
are that `is_active` is read from `users` on every request, so removing someone takes
effect immediately, and that rotating `SESSION_SECRET` invalidates every session at
once. Access is the real revocation point.

## Alternatives rejected

**Password login.** Rejected outright — see above.

**OAuth via Google/GitHub.** Workable, but it puts a third party in the login path for
an app whose entire threat model is "nobody but us", and it does not remove the need
for an allowlist. Access already provides identity, so this would be a second identity
system doing the same job.

**Access alone, no application auth.** Tempting: it is the layer that actually matters.
Rejected because `current_user` has to resolve to *something* for the ownership maths,
and deriving that from a header the origin does not verify means the app has no idea
who it is serving if Access is ever bypassed or misconfigured.

**Application auth alone, no Access.** Rejected because it puts a hand-rolled auth
surface on the public internet as the only thing between an attacker and the data.

### What the first attempt taught us

The verification initially failed in the worst way: **everyone** got 403, including the
owner, authenticated, through Access.

`fly.web.toml` shipped with `CF_ACCESS_TEAM_DOMAIN` derived from the application's own
domain name. Cloudflare *assigns* team domains, and the real one was unrelated. The
guessed host 404s on `/cdn-cgi/access/certs`, so the origin could not fetch the signing
keys, every assertion failed to verify, and the check refused all traffic — behaving
exactly as designed, against the wrong issuer.

Two things changed as a result:

- The value in `fly.web.toml` carries a comment saying Cloudflare assigns it and that
  it is not derived from your domain.
- **The rejection reason is logged**, with the issuer it tried. The response stays a
  bare 403 — it must not tell an attacker which half of the check they failed — but a
  misconfiguration that locks out the owner and says nothing is its own outage.
  `fly logs -a pfa-web` now answers it in one line.

The general lesson is about the config, not the code: a plausible-looking wrong default
is worse than an obviously empty one, because it survives review.
